# SPEC-HARDEN — стабильность ключей + защита выдачи

Две задачи: (1) чтобы купленный ключ как можно реже «переставал работать» (сервер умер) — быстро
выявлять мёртвые и держать подписку всегда из живых; (2) затруднить «расшифровал base64 → забрал
сырые vless». Только совместимые добавления; цены/заказы/маршруты не ломать. Русский.

## Часть 1 — Стабильность (сервер умер → клиент не остаётся без доступа)

Причина: подписка динамическая (собирается из alive при каждом запросе), НО (а) мёртвый сервер попадает
в alive до следующего healthcheck (сейчас раз в 10 мин, вместе с обновлением источника); (б) клиентское
приложение обновляет подписку редко. Меры:

1. **Частый независимый healthcheck.** `config.HEALTHCHECK_INTERVAL_MIN` (env, дефолт `3`). В inventory.js
   — ОТДЕЛЬНЫЙ таймер (помимо refresh источника раз в FETCH_INTERVAL_MIN): каждые HEALTHCHECK_INTERVAL_MIN
   прогонять `runHealthcheck()` (блэклист + TCP-живость с сейфгардом, как уже есть). Так мёртвый сервер
   выпадает из alive за ≤3 мин. Таймер `.unref()`, ошибки глотать, не накладываться на уже идущий прогон
   (флаг «в процессе»).
2. **Подписка всегда из живых + добор.** `configsForRegionsQty(qtyMap)` (db.js) — уже берёт alive; убедиться:
   для региона берём РОВНО min(qty, aliveCount) СВЕЖИХ живых (сорт по last_seen DESC затем hash для
   стабильности), а если живых < qty — добираем оставшиеся живые того же региона (не мёртвые!). Мёртвые
   (alive=0) в подписку не попадают НИКОГДА (даже как fallback), кроме случая «в регионе 0 живых» — тогда
   deep-fallback (самый свежий, помечен) чтобы ссылка не была пустой, но это край.
3. **Меньше интервал обновления подписки.** buildSub header `profile-update-interval` → `config.SUB_UPDATE_HOURS`
   (env, дефолт `1`; допускается дробное? нет — целое, но можно поставить меньше нельзя <1 по спеке клиентов,
   оставить 1). Дополнительно: НЕ кэшировать `/s/:token` (Cache-Control: no-store — проверить, что так).
   Клиенты Happ/v2ray сами перечитывают по этому интервалу.
4. **Кнопка «Обновить серверы» / статус ключа.** В боте (в выдаче ключа и /profile) и на key.html — кнопка
   «🔄 Обновить серверы», которая просто заново отдаёт актуальную (живую) подписку и показывает «сейчас
   в ключе N живых серверов». Это UX-заверение + подсказка «вставь ссылку заново / нажми обновить в
   приложении». (Мы не можем форсировать refresh в чужом приложении, но подписка-ссылка не меняется, а
   контент всегда свежий.) На key.html — «серверы: N живых · обновлено HH:MM», авто-перезапрос статуса.
5. **Здоровье в выдаче.** При выдаче (sendDelivery) и в /api/key показывать реальное число ЖИВЫХ серверов
   в ключе сейчас (Σ по регионам min(qty, aliveCount)). Если по региону живых меньше купленного — мягко
   пометить «часть серверов временно недоступна, автоматически заменятся».

Приёмка ч.1: мёртвый сервер исчезает из выдачи за ≤HEALTHCHECK_INTERVAL_MIN; подписка НИКОГДА не содержит
alive=0 серверов (если есть живые); клиент видит актуальное число живых; ничего из оплаты/цены не сломано.

## Часть 2 — Защита выдачи (усложнить «декод base64 → сырые vless»)

Честное ограничение: подписку обязано читать VPN-приложение, поэтому ПОЛНОСТЬЮ скрыть сырые vless нельзя
(приложение их всё равно получит). Но можно отсечь «ленивое» подглядывание и затруднить массовый слив:

1. **User-Agent gating на `/famas/s/:token`.** Если User-Agent похож на реальный VPN-клиент (по подстрокам:
   `Happ, v2ray, v2rayNG, v2rayTun, V2Box, NekoBox, sing-box, sing_box, Shadowrocket, Streisand, Clash,
   Stash, Loon, Surge, Karing, Hiddify, FoXray, SagerNet, matsuri, ktor-client` и т.п., регистронезависимо)
   ИЛИ есть спец-параметр — отдавать base64-подписку как сейчас. Иначе (обычный браузер/curl/неизвестный
   UA) — отдавать НЕ конфиги, а мягкую заглушку: маленький текст/HTML «Открой ссылку в приложении Happ /
   v2rayTun (кнопки-ссылки на key.html)» (или редирект на `/famas/k/:token`). Список UA — в config
   (`VPN_UA_ALLOW`, дефолт-массив), env-переопределяемый. `?app=1` (или заголовок) — форс-выдача для наших
   кнопок deep-link, если понадобится.
   - ВАЖНО: deep-links `happ://add/<subUrl>` и `v2raytun://import/<subUrl>` открывают приложение, которое
     САМО дёрнет `/s/:token` со своим UA — они пройдут gate. Проверить, что реальные клиенты не режутся
     (их UA — в allow-list; при сомнении — если UA пустой/не браузерный, пропускать; резать только явные
     браузеры Mozilla/Chrome/Safari/curl/wget/python/postman).
   - Точная политика: РЕЗАТЬ только если UA явно браузерный/утилита (`Mozilla, Chrome, Safari, Edg, curl,
     wget, python-requests, PostmanRuntime, Go-http-client` без VPN-маркеров). Всё остальное (в т.ч. пустой
     UA и незнакомые клиенты) — ПРОПУСКАТЬ (чтобы не сломать реальным приложениям). Это безопаснее белого
     списка.
2. **Мягкий rate-limit по токену.** In-memory: не больше N запросов `/s/:token` в минуту с «браузерными»
   признаками; приложения (по интервалу обновления) укладываются. Не жёстко (не блокировать реальных).
   Опционально, можно простой счётчик.
3. **Честно сообщить владельцу** (в отчёте): 100% защиты нет — при желании продвинутый юзер вытащит конфиги
   из приложения; единственный радикальный способ скрыть апстрим — свой прокси-сервер (отдельная инфра,
   вне этой задачи). UA-gate убирает 95% «расшифровал в браузере».

Приёмка ч.2: `curl`/браузер по `/s/:token` получают заглушку/страницу, а реальные VPN-клиенты (по UA) —
рабочую base64-подписку; deep-links Happ/v2rayTun работают; ничего у настоящих клиентов не сломано.

## Тесты

- node --check; selftest/parse-check зелёные; healthcheck-таймер не накладывается, unref, сейфгард цел.
- /s/:token: UA `Happ/1.0` и `v2rayNG/1.x` и пустой UA → base64-подписка; UA `Mozilla/5.0…`, `curl/8`,
  `python-requests` → заглушка (не vless). Deep-link путь (?app=1 или наш UA) → подписка.
- configsForRegionsQty никогда не возвращает alive=0; при живых<qty отдаёт сколько есть живых; мёртвый
  хост через setAlive→0 исчезает из выдачи.
- key.html/бот: число живых серверов показывается; кнопка «Обновить серверы» отдаёт свежую подписку.
