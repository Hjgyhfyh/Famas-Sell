# План подключения источников AvenCores/goida-vpn-configs в Famas Store

TL;DR по коду: три места несут всю нагрузку — `util.parseSource` (парсинг+ключ дедупа), `db.upsertConfigs` (реконсиляция по `hash UNIQUE`), `inventory.doRefresh` (fetch→parse→upsert→healthcheck). Ключевой рычаг: **сменить смысл `configs.hash` с `sha256(uri)` на `sha256(canonicalKey=host:port)`** — тогда существующая машинерия `upsertConfigs` (INSERT нового hash / UPDATE существующего / деактивация отсутствующих + `seen`-сет) даёт кросс-источниковую и кросс-рефрешную дедупликацию **без изменения схемы**. Всё остальное навешивается аддитивно и под флагами.

Важный факт, проверенный по коду: `upsertConfigs` в UPDATE трогает `uri,host,port,flag,country_*,city,label,active,last_seen`, но НЕ трогает `alive` и `first_seen` (db.js:527-531). Значит при стабильном `host:port` сервер сохраняет свою историю живости между рефрешами — это то, что нам нужно.

## 1. МУЛЬТИИСТОЧНИК

**1.1. Реестр источников.** Новый файл `src/sources.js` (коммитится, редактируемый), экспортит массив:
```
{ id, url, category:'black'|'white', type:'vless'|'mixed'|'b64', enabled, heavy }
```
- Файлы **1–25** мирора → `category:'black'`, `type:'mixed'` (внутри отфильтруем vless).
- Файл **26** → `category:'white'`, `type:'mixed'` (уже чистый, дедуплицированный).
- URL-шаблон (обе формы эквивалентны, берём raw): `https://raw.githubusercontent.com/AvenCores/goida-vpn-configs/main/githubmirror/N.txt`, N=1..26.
- Источник **#2** помечаем `heavy:true` (257k строк / 63 MB) — остаётся `enabled:true`, но обрабатывается через conditional GET и **стриминговый** merge (см. §2.6, §7). НЕ выбрасывать его: это ~52k уникальных host:port, основной прирост объёма.
- Тянуть **мирор**, а не 33 первоисточника (мирор уже нормализован/раскодирован; первоисточники часто отдают по http/при отключённой TLS-проверке — лишний риск).

**1.2. Конфиг.** В `config.js`:
- `SOURCES` = `require('./sources')`, с env-оверрайдом `SOURCES_JSON` (JSON-массив) и флагом `MULTI_SOURCE` (0 → работаем по-старому от `SOURCE_URL`; 1 → по реестру). Обратная совместимость: если `SOURCES` пуст → `[{url:SOURCE_URL, category:'black', type:'vless'}]`.
- Оставить `SOURCE_URL` как есть (fallback + текущий дефолт igareck).

**1.3. Периодичность.** Переиспользуем таймер `inventory.start()` (`FETCH_INTERVAL_MIN`). В `doRefresh` — тянем ВСЕ enabled-источники пулом (concurrency ~6, per-source timeout 30s, 1 ретрай), каждый с conditional GET (ETag/Last-Modified в `settings`, ключ `etag:<id>`/`lastmod:<id>`). Мирор апдейтится ~раз в час — большинство циклов вернут 304 и не будут перекачиваться.

## 2. ПАРСИНГ РАЗНЫХ ФОРМАТОВ

**2.1. Продаём только vless (96%).** Не-vless (trojan/ss/vmess/hysteria2/ssr/socks5/tuic ≈ 4%) **игнорируем на парсинге**. Расширять модель под них НЕ надо: вся наша выдача (`subscription.buildSub`, `rebrandUri`, deeplinks happ/v2raytun/v2rayng, клиенты) заточена под vless — поддержка др. протоколов протекла бы в subscription/UI/клиентов при копеечной отдаче. Ввести `ALLOWED_PROTOCOLS=['vless']` в config; счётчик отброшенных — в лог `refresh`.

**2.2. `parseSource(text, opts)` — обобщить (util.js).** Сейчас он line-based и берёт только строки `vless://`, дедуп по `hash=hashUri(uri)`. Изменения:
- **base64-подписка** (нужно для #16/#22 при прямой тяге; мирор уже раскодирован, но делаем устойчиво): `maybeDecodeB64(text)` — если тело без `://`, но валидный base64 → декодировать перед разбором.
- **склеенные строки**: нормализатор вставляет `\n` перед каждым `vless://` (некоторые источники клеят конфиги в одну строку).
- **внутрифайловые дубли** (в 1.txt/2.txt есть точные повторы) — снимаются автоматически новым ckey-дедупом.
- `opts = {category, type, allow}`; каждый возвращаемый конфиг получает поле `category` (для `list_type`).

**2.3. Заголовки (`# profile-title` и т.п.)** теперь шум (26 источников). `meta` оставить, но использовать только для диагностики; на каталог не влияет.

**2.4. Канонический ключ и представитель** — считаются здесь (см. §3).

**2.5. Тесты.** Расширить `scripts/parse-check.js`: семплы из scratchpad (`gm/1..26.txt`, `samples.txt`) — проверить, что vless извлекается, не-vless отбрасывается, ckey-дедуп схлопывает известные повторы, whitelist-файл маркируется.

**2.6. Память для #2 (критично).** НЕ «распарсить в массив 257k → потом дедуп». Merge делаем **стримингово-редьюсом** в общий `Map<ckey, bestRep>`: итерируем строки, для каждой считаем ckey и обновляем Map через `pickBest`. Пик памяти ~52k объектов вместо 257k. Реализовать как `mergeInto(map, text, opts)` (util или inventory), а `doRefresh` кормит один Map со всех источников и в конце отдаёт `map.values()` в `upsertConfigs`.

## 3. ДЕДУПЛИКАЦИЯ (ядро, «никаких повторок»)

**3.1. Канонический ключ сервера.** `canonicalKey = lower(host) + ':' + port`.
- host уже без скобок IPv6 (`parseHostPort` их срезает), домены в lowercase, порт числом.
- Это даёт заявленные ~56k уникальных серверов из 312k строк (host:port-дедуп убирает 82% семантических повторов; дедуп по полной строке убрал бы лишь 6% — недостаточно).
- **Опция строже**: `host:port:uuid` — если владелец заметит «порт живой, но конкретный uuid мёртв» (мультитенант за одним host:port). Это правка одной строки в `canonicalKey`. Веду по `host:port` (честная единица «сервер», совпадает с 56k и с логикой `file_manager.py`); uuid-вариант — как явный переключатель `DEDUP_INCLUDE_UUID`.

**3.2. Репозиторий ключа = существующий `configs.hash`.** Сменить в `parseVlessLine`: `hash = sha256(canonicalKey)` вместо `hashUri(uri)`. Тогда БЕЗ изменения схемы:
- один и тот же сервер из 5 источников → один hash → `upsertConfigs` `seen`-сет (db.js:537) схлопывает в ОДНУ строку;
- между рефрешами host:port стабилен → hash стабилен → `alive`/`first_seen` сохраняются (UPDATE их не трогает);
- реконсиляция (деактивация отсутствующих) продолжает работать по hash = по канону сервера.

**3.3. Выбор представителя `pickBest(a,b)`** (какой uri/label храним при коллизии ckey). Приоритет: `security` reality > tls > none; host не в блэклисте; есть распознанная страна/флаг; наличие валидного uuid; короче/чище label. Считается в merge-редьюсе (§2.6) и/или через сортировку перед upsert (важно, т.к. `seen` оставляет ПЕРВОГО — кормить upsert уже «лучшими»).

**3.4. Разовая миграция существующей БД.** Текущие строки имеют `hash=sha256(uri)`. Идемпотентная миграция в `db.migrate()`: для каждой строки вычислить `canonicalKey`→новый hash; при коллизиях (несколько старых строк → один ckey) оставить одну (max `last_seen`, затем best), лишние удалить; проставить новый hash. Обходит нарушение `hash UNIQUE` и убирает разовый «мусорный» рефреш (иначе первый refresh массово деактивирует старые и вставит новые — не смертельно, но шумно; миграция чище).

**3.5. `upsertConfigs`** — минимально: добавить в params/INSERT/UPDATE поле `list_type` (см. §4). Логика реконсиляции не меняется.

## 5. АВТОНОМНАЯ ПРОВЕРКА / ПИНГ (масштаб ×100)

**5.1. Проблема масштаба.** Хостов на проверку: ~500 → ~56k (distinct host:port). При нынешних `concurrency=24`, `timeout=4000` полный проход ≈ 56000/24×4с ≈ **2.6 часа** — несовместимо с интервалом 3 мин.

**5.2. Ротация вместо «всё каждый цикл».** Добавить колонку `alive_checked_at INTEGER`. `hostsToCheck(limit)` возвращает **самые давно проверенные первыми** (`ORDER BY alive_checked_at ASC NULLS FIRST`), батч ограничен (`HEALTHCHECK_BATCH`, напр. 6–10k). Новые (никогда не проверенные, `alive` дефолт 1) — в приоритете. Полный свип набирается за несколько циклов; каждый сервер перепроверяется в целевом окне (напр. ≤15–20 мин).

**5.3. Конкурентность/тайминги.** Поднять `HEALTHCHECK_CONCURRENCY` до 200–400 (Node тянет; следить за лимитом FD/эфемерных портов на VDS — можно `ulimit -n`), `timeout` 3000. Тогда батч 8k при conc 300 ≈ 80с. Пул `runPool` уже готов, менять не нужно.

**5.4. Сейфгард 85%.** Сейчас глобальный (inventory.js:163). На «грязных» источниках (иранские/free — высокий % дохлых) он может срабатывать и НЕ применять TCP вовсе. Сделать **по-батчево** (проверять долю в рамках батча) и/или поднять порог/добавить абсолютный минимум проверенных. Иначе живость не будет обновляться.

**5.5. Блэклист.** `HOST_BLACKLIST` через `setAliveByHostPattern` остаётся; на 56k работает так же. Ожидаемо много free-хостов из Telegram-агрегаторов — блэклист можно расширить.

**5.6. Реальная проверка через прокси — оценка.** TCP-connect подтверждает лишь «порт открыт», НЕ то, что vless/REALITY-хендшейк и uuid валидны. Полноценная проверка = поднять xray-core/sing-box на каждый конфиг и сходить на канарейку — секунды на конфиг, для 56k непрерывно **нереально**. Рекомендация:
- v1: TCP-gate (как есть) + ротация.
- Дёшево усилить: для tls/reality-конфигов — `tls.connect` с проверкой, что порт реально говорит TLS/ALPN (Node `node:tls`, ~как TCP по цене) — отсеивает больше мёртвых, чем сырой TCP.
- Полный proxy-probe — только как **офлайновый сэмпл-аудит** (отдельный скрипт, выборка/по расписанию), не инлайн.

**5.7. Дедуп уже снизил нагрузку в ~6×** (проверяем 56k, а не 312k) — healthcheck-бюджет реалистичен.

## 6. РЕГИОНЫ (GeoIP)

**6.1. Проблема.** Сейчас страна = флаг-эмодзи из `#fragment` → ISO, иначе имя в тексте, иначе `XX` (util.js:370-406). Во всём репо флаг проставлен лишь у **4.7%** → подавляющее большинство новых конфигов упадёт в `XX` = непродаваемо/уродливо в каталоге. Это блокер, без него мультиисточник почти бесполезен для витрины.

**6.2. Решение — GeoIP по IP.**
- Библиотека: **`geoip-lite`** (офлайн, встроенная БД, без API-ключа, CommonJS, MIT) — минимум трения для Node18. Альтернатива полегче по размеру: `mmdb-lib` + GeoLite2-Country.mmdb (~9 MB, но нужен MaxMind-аккаунт для обновлений). Веду `geoip-lite`.
- Пайплайн (отдельный enrich-пасс, как healthcheck, не блокирует upsert): host часто домен → `dns.resolve4/6` → IP → `geoip.lookup(ip).country` → ISO. Для host-IP — прямой lookup.
- Приоритет: **валидный флаг/распознанное имя из фрагмента остаётся** (быстрый путь и уважение к явной метке), GeoIP **заполняет только `XX`** (и опц. чинит явно неверные). Теги (`#`) ненадёжны (эмодзи/CJK/urlencoded) — не доверять сверх флага.
- Кэш `host → {ip, iso, at}` (колонка `geo_checked_at` + маленькая таблица/`settings` или in-memory Map с TTL): DNS+geoip только для новых/изменённых хостов. 56k разово, дальше инкрементально.
- CDN/Cloudflare-фронт: host резолвится в anycast CDN → GeoIP даст локацию CDN, не выхода. Best-effort; опц. детект известных CDN-диапазонов → оставить `XX` или метку. `rebrandUri` всё равно переписывает лейбл на брендовый, так что для клиента это только группировка.

**6.3. Результат.** С ~15 «флаговых» регионов сегодня → **~100+** реальных (в репо видно 105 стран). Продаваемых (с ≥1 живым) реалистично 60–90.

4. **`db.js`** — миграции (идемпотентно): `list_type`, `orders.list_type`, `alive_checked_at`, `geo_checked_at`, новый индекс; разовая collapse+rehash-миграция (§3.4); `list_type` в `upsertConfigs`; `listType`-параметр в региональных запросах; `hostsToCheck(limit)` с ротацией; `setGeo(host,iso)`.

**Риски (по убыванию):**
- **#1 — деактивация при сбое источника.** `upsertConfigs` деактивирует всё, чего нет в переданном наборе. Если источник не скачался, его серверы исчезнут из продажи. **Митигация обязательна**: запускать реконсиляцию (деактивацию) только когда ВСЕ enabled-источники отдали 200/304; иначе — держать per-source last-good (кэш текста в `data/cache/<id>.txt` или в settings) и мержить его, чтобы набор был полным. Частичный fetch → не деактивировать.
- **Разовый churn hash** — снимается collapse-миграцией (§3.4); иначе один шумный рефреш.
- **#2 (63 MB)** — время/память: conditional GET + стриминговый merge (§2.6); флаг отключения `heavy`.
- **Сейфгард 85%** глобально тормозит живость на грязных источниках → сделать по-батчево (§5.4).
- **geoip-lite** — вес офлайн-данных и добавление зависимости; проверить сборку/размер на VDS.
- **Рост БД** — 56k строк для SQLite норм; следить за `events` (уже растёт).

**Откат:** `MULTI_SOURCE=0` → работа от одного `SOURCE_URL` как сейчас. Колонки (`list_type` и пр.) безвредны при неиспользовании. GeoIP/whitelist — независимые флаги. Единственное необратимое — collapse+rehash БД: перед миграцией сделать копию `data/famas.db` (WAL) для быстрого отката.
